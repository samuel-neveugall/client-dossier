<objective>
Give `dossier-init` its adoption half: detect the folders and files of an existing repository
that already play a dossier role under other names, and print an ordered, confirmable proposal
of `git mv` renames to the fixed English names — writing nothing.

Purpose: ROADMAP criterion 4 and SCAF-06. This is what makes the plugin adoptable by a
repository that already holds a real engagement instead of only by an empty one. The proposal is
deterministic and diffed against a golden file, so the mapping can be reviewed at planning time
rather than improvised at adoption time.
Output: `--propose-renames` in `init.py`, a throwaway fixture builder, the golden proposal, and
the test that ties them together.
</objective>

Add `RENAME_TABLE`, `propose_renames(root)` and the `--propose-renames` flag. Standard library

`RENAME_TABLE` — a one-way adoption table, used once at init and never as a runtime mapping
(CLAUDE.md C-3). Three groups of literals:
- top-level directories: `dossier`, `client`, `relation`, `relationship` → `dossier`;
  `knowledge`, `docs`, `connaissance`, `connaissances` → `knowledge`;
  `outbound`, `communication`, `sortant` → `outbound`; `sources` → `sources`;
- child directories, matched only inside a mapped parent: `appels`/`calls` → `calls`;
  `livrables`/`deliverables` → `deliverables`; `mails` → `mails`; `veille`/`watch` → `watch`;
  `decisions` → `decisions`; `transcripts` → `transcripts`; `raw` → `raw`;
- files, matched only inside a mapped parent: `ACTEURS.md` → `ACTORS.md`,
  `APPRENTISSAGES.md` → `LEARNINGS.md`, `CANAUX.md` → `CHANNELS.md`,
  `HISTORIQUE.md` → `HISTORY.md`, `QUESTIONS-OUVERTES.md` → `OPEN-QUESTIONS.md`,
  `RELATION.md` → `RELATIONSHIP.md`, `TON.md` → `TONE.md`, `CONTEXTE.md` → `CONTEXT.md`.
Matching is case-insensitive on the name; the emitted target is always the fixed English literal.

`propose_renames(root)` — pure inspection. It reads the filesystem and runs `git`, and it writes
nothing, creates nothing and moves nothing. For each immediate subdirectory of `root`:
- resolve it with `os.path.realpath` and, when the result is not under the resolved root, emit an
  `unsafe:` entry and move on — a symlink out of the repository must never be handed to `git mv`;
- look the name up in the top-level table. A hit that already equals its target emits nothing for
  the directory itself but still recurses into it; a hit that differs becomes a rename entry;
- a miss is examined for content hints: a directory holding at least two names from the living-file
  set, in either language, becomes a `candidate:` entry naming the role it looks like — reported
  for a human to confirm, never proposed. A miss with no hint becomes an `ignored:` entry with the
  no-role reason;
- inside a mapped parent, apply the child-directory and file tables. A `sources/` subdirectory that
  the table does not name becomes an `ignored:` entry naming the spec-layout reason (this is
  RESEARCH DISC-1, decided in this plan's Deviations section, not an omission);
- probe every rename candidate with `git ls-files --error-unmatch -- <path>` before proposing it;
  a non-zero result moves the entry from the rename section to the untracked section, with the
  arrow kept and the history warning appended. Run `git` through `subprocess.run` with an argument
  list and `shell=False`, capturing output — never a command string, never `os.system`. When `git`
  itself is absent or the directory is not a repository, treat every candidate as untracked and
  say so once, rather than raising (CLAUDE.md C-8).

Path composition follows the execution order: child entries are expressed against the parent's
*new* name, so the printed list can be applied top to bottom. Every path in the output goes
through `shlex.quote`, so the skill can paste it straight into `git mv -- <old> <new>` in plan
01-06 without building an injectable string.

Emit, in this order: the summary line
`propose-renames: <n> proposed, <n> untracked, <n> unsafe, <n> ignored`, then the `rename:` lines
grouped by top-level candidate in lexicographic order of the original name with children sorted
lexicographically, then `untracked:`, then `unsafe:`, then `candidate:`, then `ignored:` — each of
those four sorted lexicographically. Determinism is the point: the golden diff is the acceptance
test, so two runs on the same tree must produce identical bytes.

Wire `--propose-renames` into `main` as a mode that runs `propose_renames`, prints, and returns 0
**before any scaffolding happens**. It takes no confirmation and performs no rename: executing the
`git mv` commands after an explicit human confirmation is the skill's job (D-15), and the script
never commits anything either way.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| an existing repository's tree → `propose_renames` | directory and file names, symlinks and the git index all come from a repository the plugin did not create |
| the proposal's text → the `git mv` command the skill runs through a shell (plan 01-06) | every emitted path crosses into a shell one step later |
| the origin engagement repository → this phase's deliverables | confidential content that must never cross into a template, fixture, golden file or commit message |
