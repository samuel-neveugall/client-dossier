## Script contract (fixed here; plan 04-04's SKILL.md reports from it)

`extract-text.sh FILE.pdf` (also `.PDF`):
- 0 and stdout `extracted: <stem>.txt` — a new `.txt` written next to the PDF;
- 0 and stdout `exists: <stem>.txt` — already there (file or symlink), untouched;
- 64 — usage: no argument, not a `.pdf`, or no such file;
- 65 — no text layer (a scan): nothing written, stderr says so;
- 69 — `pdftotext` not on PATH: the two stderr lines of must_haves, nothing written;
- 1 — pdftotext failed (its own message passed through), nothing written.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| a received PDF -> pdftotext | untrusted file content parsed by a system tool |
| the script -> sources/ | the only writer of the `.txt`; the Phase 3 guard cannot see it |
| a PDF file name -> the pdftotext command line | the name is user- or sender-chosen |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-04-20 | Tampering | overwriting an existing `.txt` under sources/ (the guard does not inspect pdftotext or bash scripts) | high | mitigate | `[ -e ] \|\| [ -L ]` pre-check plus the final write under `set -C`; tested for an existing file, a dangling symlink and a race with a fake pdftotext |
| T-04-21 | Tampering | a partial or garbage `.txt` left under sources/ after a crash or a corrupt PDF | medium | mitigate | pdftotext writes to a temporary file outside the dossier; the `.txt` is written once at the end; tested with a corrupt PDF and a scan (nothing written) |
